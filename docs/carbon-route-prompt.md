## 2. 功能目標

旅客在**地圖頁**挑選最多 **8 個**想去的景點，選擇起點與人數，按「查詢路線」後，系統針對**每一段路**列出可用的交通方式，顯示每種方式的**時間**與**碳排放量**，並用固定規則給出**建議**。

### 設計原則（務必遵守）

1. **目的地由旅客決定。** 不因碳排高就勸旅客不要去某個景點；而是針對旅客已選好的景點，建議碳排較低的交通方式。語氣是「提供選擇」，不是「責備」。
2. **碳排是路線標籤，不是獨立的計算器。** 它出現在「查詢路線」的結果旁邊，不要做成一個獨立的「碳排計算」功能頁。
3. **不只給數字，要給建議。** 同時顯示時間，讓旅客自己取捨；並顯示與「汽車」的差額。
4. **誠實標示不確定性。** 估算值一律標註，並提供「計算方式與資料來源」的說明。
5. **純前端、固定公式、離線可用。** 不呼叫後端、不呼叫 AI、不在使用者操作時打任何需要金鑰的 API。

## 4. 碳排放係數：資料研究與取用規則

### 4.1 資料來源與優先順序

請依序使用，且**每個係數只採用有出處的數字**：

| 等級 | 來源 | 畫面標示 |
| --- | --- | --- |
| **等級 1（優先）** | 政府資料開放平臺 data.gov.tw 的官方資料集：<https://data.gov.tw/datasets/search?p=1&size=10&s=_score_desc&cgl-3=44585> （此為篩選後的資料集分類頁，請在其中尋找與碳排放、碳足跡、排放係數、運具、能耗相關的資料集） | 「官方資料」 |
| **等級 2（補足）** | 其他**有出處**的來源：環境部、能源署等政府機關公告、業者（如臺鐵、高鐵、捷運公司）公告或查證過的碳足跡標籤、學術研究 | 「估算」＋來源 |
| **等級 3** | 以上都找不到 | 該交通方式**不顯示**，絕不編數字 |

**不可採用的來源：** 沒有出處的網路文章、記者或網友用 ChatGPT 之類工具自行計算的數字、年度與單位不明的數字。

### 4.2 如何進行研究

1. 從上述網址開始，找出所有可能相關的資料集；**把候選清單與你的判斷寫成 `docs/carbon-sources.md`**（資料集名稱、提供機關、連結、欄位、授權、更新日期、適用的交通方式、採用或不採用的理由）。
2. **若 data.gov.tw 禁止自動讀取（robots 限制）：** 不要繞過限制。改用你有的瀏覽器工具逐頁查看；若仍無法讀取，請使用者下載 CSV 後放進專案資料夾，或直接把資料集名稱與內容貼給你。
3. 讀取 CSV 時請檢查編碼（常見為 UTF-8，也可能有 BOM 或 Big5）。
4. 若同一交通方式有多筆資料（例如依速率或道路類型分類），**選一個清楚的規則並寫下來**（例如依路段長度或市區／公路取代表速率），不要隨意取平均而不說明。
5. 這個步驟結束後**必須停下來，把結果給使用者審閱**（見 Phase 0 的驗收），使用者確認係數之前不可進入下一階段。

### 4.3 單位與換算（極重要）

- 係數有兩種基準，**一定要分清楚並在資料中明確記錄**：
  - `per_passenger_km`：每人每公里（例如鐵路、有些業者公告）
  - `per_vehicle_km`：每輛車每公里（例如許多車輛排放資料集）
- 若來源是**每輛車**，要換成每人時，必須使用「載客人數」假設，**該假設也必須有出處**；沒有出處就在畫面標示為「估算」。
- 溫室氣體單位統一為 **g CO₂e／公里**（或 kg），換算時小心 g 與 kg。
- 步行與一般腳踏車的行駛排放視為 **0**，並在說明中註明「僅計算行駛過程，不含製造與生命週期排放」。

### 4.4 係數檔案格式（`carbon/carbon-factors.json`，人工整理，非自動產生）

```json
{
  "version": "資料整理日期",
  "retrievedAt": "YYYY-MM-DD",
  "factors": {
    "car": {
      "available": true,
      "basis": "per_vehicle_km",
      "gCO2e": 0,
      "tier": 1,
      "year": 0,
      "source": { "name": "", "org": "", "url": "", "license": "" },
      "notes": ""
    }
  },
  "assumptions": {
    "carCapacity": { "value": 4, "source": "assumption" },
    "motorcycleCapacity": { "value": 2, "source": "assumption" },
    "busOccupancy": { "value": null, "source": "" }
  }
}
```

> 上面的 `0` 與 `null` 只是格式範例，**不是真實數字**。所有真實數值必須來自 §4.1 的來源。
> 找不到的交通方式：`"available": false`，並在 `notes` 說明原因。

## 5. TDX 運輸資料：先檢查能不能用

專案已經有 TDX 帳號與金鑰（放在 GitHub Secrets），目前用來取得觀光資料。本功能希望**盡可能使用 TDX 的運輸資料**，以判斷某個地點附近有沒有捷運、臺鐵、高鐵、公車可搭，但**不確定現有金鑰是否有權限**。

### 5.1 檢查流程（Phase 0 的一部分）

1. 閱讀現有的 GitHub Actions workflow 與 Node.js 資料更新腳本，找出：金鑰在 Secrets 中的名稱、取得 token 的方式、已有的重試與限流處理。
2. 在**本機**用環境變數（`.env`，已在 `.gitignore`）測試：以現有金鑰取得 token，並嘗試呼叫運輸類資料（捷運站位、臺鐵車站、高鐵車站、公車站牌）。到 TDX 官方文件確認正確的 API 路徑，**不要憑記憶猜路徑**。需要使用者提供本機環境變數時，請向使用者要，**不要印出金鑰內容**。
3. 判斷結果寫成 `docs/transit-decision.md`：
   - **能用** → 採用「TDX 模式」
   - **不能用**（401／403、無權限、額度不足等）→ 採用「MVP 模式」（不靠 TDX）
4. **兩種模式都要支援腳踏車與步行。** 程式要能在缺少 TDX 資料檔時，自動退回 MVP 模式（不要壞掉）。

### 5.2 TDX 模式的資料設計

前端是靜態網頁，所以**運輸資料也做成靜態檔**，由 GitHub Actions 的腳本產生：

- `data/transit_stations.json`：捷運、臺鐵、高鐵的車站（名稱、經緯度、系統別、所屬城市）。數量不大，前端可整份載入，用 haversine 找出**任何一點**（含旅客自選的起點）最近的車站。
- `data/bus_access.json`：公車站牌數量很大，**不要整份放前端**。腳本預先算出**每個景點**到最近公車站牌的距離（用空間格網加速，避免 O(n×m) 全部比對），只輸出小檔案。
- 沿用現有腳本的重試與備援機制：某一類取得失敗時，保留上次的檔案。
- 新增 workflow 步驟需要改動 `.github/workflows/`：**修改前先問使用者**。
- 公車到站、即時資料**不做**（需要伺服器且不穩定）。

### 5.3 MVP 模式（不靠 TDX）的可行性判斷

沒有站位資料時，無法知道附近有沒有站，因此：

- 步行、腳踏車、機車、汽車：只看距離。
- 公車、臺鐵、高鐵：僅在距離落在合理範圍時顯示，並標註「**估算，需確認站點**」。
- **捷運：不顯示**（完全無法判斷）。
- 各交通方式的距離範圍是**設定值**（§6.3），不要寫死在各處。

## 6. 計算規則（`carbon/carbon-core.js`，純函式）

### 6.1 距離

- 兩點之間用 **haversine 直線距離 × 繞路係數** 估算實際距離（預設 1.3，設定值）。
- 這是估算，結果標註「距離為估算值」。
- 起點與終點相同或距離為 0 的段落：略過並提示。
- 同一景點重複加入：不允許。

### 6.2 碳排

對每一段、每一種可用交通方式：

- **每人基準的交通方式**（鐵路、捷運、公車等，視係數基準而定）：
  `總碳排 = 每人每公里係數 × 距離 × 人數`
- **每輛車基準的交通方式**（汽車、機車）：
  `車輛數 = ceil(人數 ÷ 載客數)`，`總碳排 = 每車每公里係數 × 距離 × 車輛數`
  載客數預設：汽車 4、機車 2（設定值，標註為「假設」）
- 同時輸出 **總碳排** 與 **每人碳排**（總碳排 ÷ 人數）。
- 公車這類「每車基準」的資料，若要換成每人，使用 §4.3 的載客人數假設。
- **基準比較對象：** 同樣人數、同一段距離**全程開汽車**的碳排。顯示「比開車少／多 X kg CO₂e」。

### 6.3 時間（設定值，皆為假設並標註「估算」）

`時間 = 距離 ÷ 平均速度 + 固定等待時間（大眾運輸）`

| 交通方式 | 平均速度與等待（初始值，可調整，都是假設） |
| --- | --- |
| 步行 | 約 5 km/h |
| 腳踏車 | 約 15 km/h |
| 公車 | 約 20 km/h ＋ 等車約 10 分鐘 |
| 捷運 | 約 35 km/h ＋ 等車約 5 分鐘 |
| 臺鐵 | 約 50 km/h ＋ 等車約 10 分鐘 |
| 高鐵 | 約 200 km/h ＋ 等車與進出站約 20 分鐘 |
| 機車 | 約 30 km/h |
| 汽車 | 約 35 km/h |

- TDX 模式下，大眾運輸段還要加上「從出發地走到車站」與「從車站走到目的地」的步行時間（步行速度同上）。
- **距離上限（設定值，初始值）：** 步行 ≤ 2.5 km；腳踏車 ≤ 15 km；機車 ≤ 100 km；公車 MVP 模式顯示範圍 1.5～80 km；高鐵 MVP 模式顯示範圍 ≥ 50 km；臺鐵 MVP 模式顯示範圍 ≥ 10 km。
- TDX 模式下車站可達距離（設定值）：捷運 1.0 km、臺鐵 1.5 km、高鐵 3.0 km 以內才視為可搭；公車以「最近站牌距離」判斷（景點端用 `bus_access.json`，起點端若無資料則標「估算，需確認站點」）。
- 以上所有數字都是**初始假設**，必須集中放在一個設定物件，並在「計算方式」說明中公開。

### 6.4 每段至少兩種方式

1. 先列出**有資料依據**的可用方式。
2. 若不足兩種，用**等級 2 估算**的方式補足（標註「估算」＋來源）。
3. 汽車與機車（若在距離範圍內）幾乎永遠可用，因此通常能達到兩種；若仍不足，顯示提示「這一段目前資料不足，僅供參考」。
4. 沒有任何出處可用的交通方式，**不補、不編**。

### 6.5 標籤（每個選項都要清楚標示）

| 標籤 | 意義 |
| --- | --- |
| 官方資料 | 係數來自 data.gov.tw 官方資料集（等級 1） |
| 估算・係數 | 係數來自等級 2 的來源 |
| 估算・距離／時間 | 距離或時間為估算（幾乎所有選項都有，可合併成一個全域說明，不用每個選項重複顯示） |
| 需確認站點 | 僅在 MVP 模式，大眾運輸是否真的可搭並未驗證 |

### 6.6 建議規則（固定規則，不用 AI）

對**每一段**：

1. 找出**最快**的方式（時間最短）。
2. 定義「合理時間」：`時間 ≤ max(最快時間 × 1.5, 最快時間 + 20 分鐘)`。
3. 在「合理時間」內，**碳排最低**的方式 = **建議**。
4. 另外標出「最低碳」與「最快」。
5. 產生一句建議（模板化文字，多語言放在 strings 檔），例如：
   「這一段建議{方式}，比{汽車}少排約 X kg CO₂e（每人 Y kg），約多花 Z 分鐘。」
6. 若建議的方式就是汽車，直接說明即可，**不要有責備語氣**。
7. 旅客可以自己改選任何一種方式；預設選中「建議」。

整趟行程：顯示所選方式組合的**總碳排、總時間**，以及與「每段都開汽車」相比少排多少。

   - **起點**：「在地圖上點選」模式 ＋「使用目前位置」按鈕；起點用不同於景點的標記顯示
   - **人數**：1～10
   - 「**查詢路線**」按鈕
3. 查詢後，每一段顯示一張卡片：「起點 → 景點」，其下列出各交通方式：名稱、時間、總碳排（每人）、與汽車差額、標籤；單選方式；預設選中建議並標出「建議」。
4. 結果最下方顯示整趟總碳排、總時間、與全程開車的差額。
5. **地圖上用直線連接各點**（依所選方式用不同顏色），並**明確標註「示意直線，非實際路線」**。
6. 提供「**計算方式與資料來源**」說明視窗：列出每個係數的來源、年度、單位、假設值，以及「估算」的意義。
7. 畫面上要有簡短免責說明：「碳排為估算值，僅供參考」。
8. 行動裝置與桌機都要能用；日夜模式都要正常（沿用專案現有的 CSS 變數與配色）。
9. **安全：** 資料檔中的文字（景點名稱、來源名稱等）一律用 `textContent` 或轉義後顯示，**不要用 `innerHTML` 插入未消毒的資料**。

## 9. 檔案結構與所有權

```
carbon/                          # B（使用者）擁有，本功能全部放這裡
├─ carbon-core.js                # 純函式，無 DOM，可在瀏覽器與 Node 使用（UMD）
├─ carbon-config.js              # 所有假設值與設定（速度、距離上限、載客數、繞路係數…）
├─ carbon-factors.json           # 人工整理的係數（含出處，§4.4）
├─ transit.js                    # 載入與使用車站／公車可達資料；缺檔時退回 MVP 模式
├─ route-panel.js                # 介面：行程面板、結果卡片、地圖直線、說明視窗
├─ strings.js                    # 四種語言文字
└─ tests/
   └─ carbon-core.test.js        # 使用 Node 內建 `node --test`，不需額外套件
scripts/
└─ build-transit-data.js         # 僅 TDX 模式：產生 data/transit_*.json（沿用現有腳本風格）
data/
├─ transit_stations.json         # 自動產生，不要手改（僅 TDX 模式）
└─ bus_access.json               # 自動產生，不要手改（僅 TDX 模式）
docs/
├─ carbon-sources.md             # 資料集研究紀錄與採用決定（Phase 0）
├─ transit-decision.md           # TDX 檢查結果（Phase 0）
└─ carbon-method.md              # 計算方式摘要，可直接用於競賽的系統概述文件（Phase 4）
```

**不要動：** `backend/`、登入與集章相關的 JS、`data/locations.json`。
**可以最小幅度修改：** 主頁面（`index.html` 或對應的 JS）——只允許加入 `<script>` 引入、行程面板容器、「加入行程」按鈕的掛載點與地圖圖層。**改動前先說明並取得同意**。
**Git：** 在自己的分支作業，不推 `main`；開工前先合併最新的 `main`；不要 commit `.env`、金鑰。
**不要引入建置工具**（專案是純靜態網頁，沒有打包流程）；外部函式庫只能從 cdnjs 等 CDN 以固定版本載入，且非必要不新增。

## 11. 驗收測試

### 11.1 自動測試（Node `node --test`）

測試中的數值**必須從 `carbon-factors.json` 讀取後計算預期值**，不要把真實係數硬寫進測試。

| 項目 | 預期 |
| --- | --- |
| 汽車 10 km、4 人 | 車輛數 1 |
| 汽車 10 km、5 人 | 車輛數 2，總碳排為 4 人時的 2 倍 |
| 機車 10 km、3 人 | 車輛數 2 |
| 大眾運輸（每人基準）人數加倍 | 總碳排加倍，**每人碳排不變** |
| 步行、腳踏車 | 碳排為 0 |
| 每人碳排 × 人數 | 等於總碳排 |
| 距離 0.3 km、5 km、50 km、300 km 的每一段 | 每段都至少 2 種交通方式 |
| MVP 模式 | **不出現捷運**；公車、臺鐵、高鐵只在設定範圍內出現，且帶「需確認站點」 |
| 超過距離上限 | 步行、腳踏車、機車不出現 |
| 建議規則 | 建議的方式一定在「合理時間」內，且是其中碳排最低者 |
| 景點數量 | 第 9 個景點被拒絕；人數限制在 1～10 |
| 重複景點、起點等於景點 | 被正確處理，不產生 NaN 或負數 |
| `available: false` 的交通方式 | 不出現在結果中 |
| 所有輸出 | 沒有 `NaN`、`Infinity`、`undefined` |

### 11.2 手動測試清單

1. 加入 3 個景點、選起點、人數 1，查詢 → 每段有至少兩種方式、有建議、有標籤。
2. 人數改成 5 → 汽車與機車的總碳排與車輛數正確變動。
3. 把某一段改選另一種方式 → 整趟總計即時更新。
4. 移除或上下移動景點後重新查詢 → 結果正確。
5. 加入第 9 個景點 → 有提示且不會加入。
6. 不開定位權限 → 仍可用地圖點選起點，沒有錯誤畫面。
7. 手機寬度與日夜模式 → 版面正常。
8. 斷網（只載入已快取的頁面）→ 功能仍可使用（不依賴任何伺服器）。
9. 刪除 `data/transit_*.json` → 自動退回 MVP 模式，沒有壞掉。
10. 切換四種語言 → 文字正確，沒有顯示 key 名稱。
11. 「計算方式與資料來源」視窗內容與 `carbon-factors.json` 一致。
